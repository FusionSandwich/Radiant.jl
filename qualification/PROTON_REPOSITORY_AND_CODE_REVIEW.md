# Proton implementation review (2026-09-25)

## Radiant repository and pull requests

The public [Radiant user guide](https://cbienvenue.github.io/Radiant.jl/user_guide_getting_started/) presents the `Cross_Sections` → `Geometry` → `Solvers` → `Fixed_Sources` → `Computation_Unit.run` workflow and describes heavy charged particles as building blocks. This branch's manufactured proton solve follows that object flow. Its local `src/hts_addon/Proton_Native_Binding.jl` currently supplies synthetic stopping tables, zero nonelastic removal and a native CSD/BFP solve. The gate matrix correctly leaves physical proton transport unqualified.

The fork's [HTS foundation PR #1](https://github.com/FusionSandwich/Radiant.jl/pull/1) was closed at the user's request and explicitly kept on a development branch without a default-branch merge. This proton work likewise remains on its isolated branch.

## Features in comparable proton transport codes

This is a feature comparison, not a claim that any external code or model has been validated for the HTS materials. No external transport code was executed.

## Recommended order and acceptance evidence

1. Establish stopping truth for exact materials: reconcile PR #127 and #128 semantics, pin source artifacts and phase, test 1, intermediate and 500 MeV points plus ranges against independent matched references. Do not promote the current synthetic table fixture.
2. Connect qualified isotope-resolved elastic and multiple-scattering inputs, then add straggling and test depth/angle/lateral observables. Keep separate electronic, nuclear and recoil-handoff scores.
3. Connect nonzero nonelastic removal only with deterministic production matrices and correlated event-family/residual handoff. Reconcile mean matrices with weighted events and close all product, energy, charge and baryon accounts, including pion/muon/decay routing where relevant.
4. Retain outgoing SN boundary currents and cutoff flow, then validate source-to-deposition/leakage ledgers and cross-code phase-space replay. Couple mapped geometry and fields only after the Cartesian closure passes.
5. Set accuracy and speed acceptance cases: exact source/material/model hashes, at least one independently derived manufactured case, exact-material physical references, group/angle/mesh convergence, cold/warm wall time and peak memory on both supported Julia versions. The separate Codex benchmark task measures the current synthetic workflow; it cannot certify physical accuracy.

The critical feature choices follow the HTS target: layer heating, recoil and damage handoff, activation precursors, leakage and secondary inventories. The comparison codes show why a single depth-dose agreement would be insufficient to qualify the full 1–500 MeV model.

## Independent accuracy and speed check

A separate Codex task tested exact commit `e595628759e53d19b98a576dc64ac6fa18a973d6` in a detached local worktree. Its full method and raw-result locations are recorded in [`PROTON_INDEPENDENT_ACCURACY_SPEED.md`](PROTON_INDEPENDENT_ACCURACY_SPEED.md). All 64 targeted proton assertions passed. An exact zero-stopping SN2 control matched `sqrt(3)/2` to floating-point precision. In the two-group, two-material constant-stopping fixture, the front layer's small lower-energy flux component was 47.94% high on one voxel per material. Joint refinement to eight energy groups and 32 voxels per material reduced that component's error to 0.049%; the back component's error was 0.00024%. This makes mesh/group convergence an acceptance gate even for manufactured transport.

On one Julia 1.10.12 thread, the two-group first solve took 9.20 s including JIT compilation; the median of three warm solves was 1.20 ms with 169 kB allocation. Whole-process high-water RSS was about 1.0 GiB including Julia and compilation. These tiny synthetic cases measure integration overhead, not physical-model accuracy or production-scale speed. The independent assessment did not execute a physical proton reference, nonelastic kernel, fast SN variant or secondary transport.
